# LLM Gateway Per-User Metering/Budget Patterns and Claude Code Usage Dashboards

Research date: 2026-09-20. Scope: (a) how general-purpose LLM gateways model users/keys, budgets and limits, enforce them, parse Anthropic streaming usage, and what their dashboards show; (b) how Claude Code usage monitors source data and visualise it; (c) conventional dashboard statistics; (d) lightweight stacks. Every claim carries a URL; inferences are separated.

## Key Question 1: How do LLM gateways model users/teams/virtual keys, budgets and limits, enforce them, and parse Anthropic usage? Can they be pointed at Anthropic with an OAuth bearer token?

### Takeaway
All major gateways converge on the same design: a "virtual key" credential that bundles (1) allowed models/providers, (2) one or more spend/token budgets with a reset duration, (3) request- and token-per-window rate limits, attached to an optional hierarchy of user -> team -> organisation/customer; enforcement is pre-request (fail-fast) with 4xx errors (400/402/429), spend is written per request to a SQL log table and rolled up into per-key/user/team counters. LiteLLM is the only gateway with a documented, supported path for forwarding a Claude Code OAuth bearer token to Anthropic while still metering per virtual key; Bifrost and Portkey have no documented equivalent.

### Cited Findings

**LiteLLM proxy (BerriAI) — entity and budget model**
- Budget scopes, in enforcement order: global proxy budget (`litellm_settings.max_budget`, `budget_duration`), team budgets (`/team/new` with `max_budget`, `budget_duration`, `tpm_limit`, `rpm_limit`), team-member budgets (`max_budget_in_team`), internal user budgets (`/user/new`), virtual-key budgets (`/key/generate`), per-model budgets (enterprise, `model_max_budget: {model: {budget_limit, time_period}}`), and end-user/customer budgets (`max_end_user_budget_id`) — [LiteLLM Budgets, Rate Limits docs](https://docs.litellm.ai/docs/proxy/users)
- When a key belongs to a team, "only the team (and team-member) budgets are enforced; the key owner's personal budget does not apply." — [LiteLLM Budgets docs](https://docs.litellm.ai/docs/proxy/users)
- Multiple concurrent budget windows on one key are supported: `"budget_limits": [{"budget_duration": "24h", "max_budget": 10}, {"budget_duration": "30d", "max_budget": 100}]` — [LiteLLM Budgets docs](https://docs.litellm.ai/docs/proxy/users)
- `budget_duration` formats: `30s`, `30m`, `30h`, `30d`, `1mo` (calendar month, resets first of month), `7d` (resets Sundays midnight UTC), `24h` (midnight UTC), `1h`. With no `budget_duration` the budget never resets. The server checks for resets on a scheduler every ~10 minutes (`proxy_budget_rescheduler_min_time`/`max_time`) — [LiteLLM Budgets docs](https://docs.litellm.ai/docs/proxy/users)
- Rate limits: `tpm_limit`, `rpm_limit`, `max_parallel_requests`; `general_settings.token_rate_limit_type` selects `input`, `output` or `total` (default) token counting; `default_estimated_output_tokens` is used to pre-count when a request has no `max_tokens` — [LiteLLM Budgets docs](https://docs.litellm.ai/docs/proxy/users)
- Budget exceeded returns HTTP 400 with `{"detail": "Authentication Error, ExceededTokenBudget: Current spend for token: 7.2e-05; Max Budget for Token: 2e-07"}`; team member overspend yields `ExceededBudget: Crossed spend within team`; rate limit exceeded returns HTTP 429 — [LiteLLM Budgets docs](https://docs.litellm.ai/docs/proxy/users)
- "Budget reservation" (default on) pre-estimates the maximum request cost from the body and pricing, reserves it against the budget, rejects if the reservation exceeds the budget, and swaps in the actual cost after the response; `fail_closed_budget_enforcement: true` validates against the DB on every request when Redis degrades; models priced at 0 skip budget checks (free fallback) — [LiteLLM Budgets docs](https://docs.litellm.ai/docs/proxy/users)
- "Budgets require a database" — on DB-less deployments `max_budget` fails open with a startup warning — [LiteLLM Budgets docs](https://docs.litellm.ai/docs/proxy/users)
- Virtual key fields: `models`, `team_id`, `user_id`, `max_budget`, `budget_duration`, `temp_budget_increase`, `temp_budget_expiry`, `tpm_limit`, `rpm_limit`, `max_parallel_requests`, `duration` (expiry), `auto_rotate`, `rotation_interval`, `metadata`, `aliases`, `key_alias` — [LiteLLM Virtual Keys docs](https://docs.litellm.ai/docs/proxy/virtual_keys)
- Tables: `LiteLLM_VerificationTokenTable` (key + per-key spend), `LiteLLM_UserTable`, `LiteLLM_TeamTable` (rolled-up spend), `LiteLLM_SpendLogs` (per-request records). "Spend is automatically tracked for the key in the LiteLLM_VerificationTokenTable. If the key has an attached user_id or team_id, the spend for that user is tracked in the LiteLLM_UserTable, and team in the LiteLLM_TeamTable." — [LiteLLM Virtual Keys docs](https://docs.litellm.ai/docs/proxy/virtual_keys)
- `litellm_key_header_name` lets the proxy read the virtual key from a custom header instead of `Authorization` — [LiteLLM Virtual Keys docs](https://docs.litellm.ai/docs/proxy/virtual_keys)
- Spend log fields: `api_key` (hashed), `user`, `team_id`, `end_user`, `model_group`, `spend` (USD), `prompt_tokens`, `completion_tokens`, `total_tokens`, `request_tags`, `metadata`; cost is returned per response in the `x-litellm-response-cost` header; cache reads are priced separately from cache creation — [LiteLLM Spend Tracking docs](https://docs.litellm.ai/docs/proxy/cost_tracking)
- Reporting endpoints: `/spend/logs`, `/spend/logs/v2` (paginated), `/global/spend/report` (grouped by team/customer/key), `/user/info`. Admin UI "Usage" tab shows spend by model, key, team and tag, daily spend trend charts, spend per internal user and customer, with filtering and export — [LiteLLM Spend Tracking docs](https://docs.litellm.ai/docs/proxy/cost_tracking)

**LiteLLM — Anthropic OAuth pass-through (Claude Code Max subscription)**
- Official tutorial: set `general_settings.forward_client_headers_to_llm_api: true`; Claude Code is pointed at the proxy with `ANTHROPIC_BASE_URL`, `ANTHROPIC_MODEL`, and `ANTHROPIC_CUSTOM_HEADERS="x-litellm-api-key: Bearer <virtual_key>"`; Claude Code's OAuth token travels in `Authorization: Bearer ...` and is forwarded to Anthropic, while the virtual key in `x-litellm-api-key` is used for proxy auth, logging and budgets — [LiteLLM: Using Claude Code Max Subscription](https://docs.litellm.ai/docs/tutorials/claude_code_max_subscription)
- Maintainer statement: "LiteLLM doesn't replace or store your subscription as an API key. It acts as a proxy that forwards the authenticated Claude Code request." The discussion distinguishes Claude Code -> LiteLLM -> subscription (supported for tracking) from generic clients using a stored OAuth token (unsupported, policy risk) — [LiteLLM Discussion #20072](https://github.com/BerriAI/litellm/discussions/20072)
- Known pitfall: LiteLLM's `get_api_key()` prioritises `Authorization` over `x-api-key`; when Claude Code sends both an OAuth `sk-ant-oat-*` bearer and a virtual key in `x-api-key`, the proxy tries to validate the OAuth token as a LiteLLM key and returns 401; the proposed fix is to detect `sk-ant-oat-*` tokens and fall through to `x-api-key` — [LiteLLM Issue #29190](https://github.com/BerriAI/litellm/issues/29190)
- Earlier history of this feature: PR "support claude code auth via subscription" and a bug that OAuth tokens were not forwarded — [PR #14821](https://github.com/BerriAI/litellm/pull/14821); [Issue #19618](https://github.com/BerriAI/litellm/issues/19618); [Feature request #13380](https://github.com/BerriAI/litellm/issues/13380)

**LiteLLM — Anthropic streaming usage parsing (known bugs illustrate the pattern)**
- Issue: LiteLLM's `/v1/messages` bridge emitted `message_start` with `usage.input_tokens: 0` and the real count only in the final `message_delta`; fix PR "report the request's input tokens in the opening stream frame" — [Issue #41406](https://github.com/BerriAI/litellm/issues/41406); [PR #42102](https://github.com/BerriAI/litellm/pull/42102)
- Issue: streaming bridged to OpenAI-compatible upstream lost prompt-cache accounting (`cache_read_input_tokens: 0`); fix preserves `prompt_tokens_details.cached_tokens` into `cache_read_input_tokens` — [Issue #41067](https://github.com/BerriAI/litellm/issues/41067); [PR #41071](https://github.com/BerriAI/litellm/pull/41071)
- Fix "let a later usage event zero out stale cache counts": a later prompt-side usage event replaces stale cache counters, while output-only usage events preserve prior cache usage — [PR #40845](https://github.com/BerriAI/litellm/pull/40845)
- Other proxies got this wrong in the opposite direction: one-api-pro double-counted input and cache-read tokens by summing `message_start` and `message_delta`; llmio read only `message_delta`; initializ/forge's `StreamDelta.Usage` carried only `output_tokens` and dropped input/cache — [one-api-pro #13](https://github.com/modelbus/one-api-pro/issues/13); [llmio #71](https://github.com/atopos31/llmio/issues/71); [forge #433](https://github.com/initializ/forge/issues/433)

**Anthropic streaming spec (primary source)**
- Event order: `message_start` -> (`content_block_start`, `content_block_delta`*, `content_block_stop`)* -> `message_delta` -> `message_stop`; `ping` events may appear anywhere; `error` events may appear in-stream (e.g. `overloaded_error`, the streaming analogue of HTTP 529); unknown event types must be handled gracefully — [Anthropic Streaming Messages](https://platform.claude.com/docs/en/docs/build-with-claude/streaming)
- `message_start` carries `message.usage` with `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens` and a placeholder `output_tokens` (e.g. `"usage":{"input_tokens":2679,"cache_creation_input_tokens":0,"cache_read_input_tokens":0,"output_tokens":3}`) — [Anthropic Streaming Messages](https://platform.claude.com/docs/en/docs/build-with-claude/streaming)
- `message_delta` carries final `usage`; the docs warn: "The token counts shown in the usage field of the message_delta event are cumulative." Simple examples show only `{"output_tokens": 15}`; the server-tool example shows a full block `{"input_tokens":10682,"cache_creation_input_tokens":0,"cache_read_input_tokens":0,"output_tokens":510,"server_tool_use":{"web_search_requests":1}}` — [Anthropic Streaming Messages](https://platform.claude.com/docs/en/docs/build-with-claude/streaming)

**Portkey**
- Budget limits on API keys are cost-based ("maximum spend in USD (minimum $1)") or token-based; periodic reset options are None, Weekly ("reset every Sunday at 12 AM UTC") or Monthly ("1st of each month at 12 AM UTC"); alert thresholds notify before the hard limit; rate limits are by requests or tokens per minute/hour/day; limits attach to API keys, workspaces or provider integrations; "subsequent requests are rejected until the time interval resets"; "Available on Enterprise plan and select Pro customers" — [Portkey: Enforce Budget Limits and Rate Limits](https://portkey.ai/docs/product/administration/enforce-budget-and-rate-limit)
- Older virtual-key budget doc: "There is no time period for budget limits; they apply until the budget is exhausted"; limits could not be edited once set (duplicate the key instead); enterprise-only — [Portkey Budget Limits (docs1)](https://docs1.portkey.ai/docs/product/ai-gateway/virtual-keys/budget-limits). Note: this older page conflicts with the newer administration page that adds weekly/monthly resets; treat the newer page as current.

**Helicone**
- Rate limits are declared per request via header `Helicone-RateLimit-Policy: "[quota];w=[time_window];u=[unit];s=[segment]"`, where `u` is `request` (default) or `cents` (cost-based), `s` is `user` (requires `Helicone-User-Id`) or a custom property name; `w` is seconds with a 60 s minimum; response headers `Helicone-RateLimit-Limit`, `Helicone-RateLimit-Policy`, `Helicone-RateLimit-Remaining`; violations return 429; whether windows are sliding or fixed is not stated — [Helicone Custom Rate Limits](https://docs.helicone.ai/features/advanced-usage/custom-rate-limits)
- Example from third-party course material: "$5.00 per hour per user" via `Helicone-User-Id` plus the policy header — [The Neural Base: Rate limit by user](https://theneuralbase.com/helicone/learn/intermediate/rate-limit-by-user/)

**Bifrost (Maxim AI, Go)**
- Virtual key model: id prefixed `sk-bf-*`, `is_active`, optional `expires_at` (RFC3339), `provider_configs[]`, `budgets[]` (multi-budget), token and request rate limits (VK-level only). Hierarchy: Customer -> Team -> Virtual Key -> Provider Config; a VK "Belongs to either one team OR one customer OR neither (mutually exclusive)" — [Bifrost Virtual Keys docs](https://docs.getbifrost.ai/features/governance/virtual-keys)
- Budget object: `max_limit` (USD), `reset_duration` (`1m`, `1h`, `1d`, `1w`, `1M`, `1Q`, `1Y`), `current_usage`, `last_reset`, optional `calendar_aligned` flag for UTC-boundary resets instead of rolling windows — [Bifrost Virtual Keys docs](https://docs.getbifrost.ai/features/governance/virtual-keys)
- Rate limits: `token_max_limit`/`token_reset_duration`, `request_max_limit`/`request_reset_duration` — [Bifrost Virtual Keys docs](https://docs.getbifrost.ai/features/governance/virtual-keys)
- Headers accepted: `x-bf-vk`, `Authorization: Bearer sk-bf-*`, `x-api-key`, `x-goog-api-key`, `api-key`. Error codes: 401 `virtual_key_required`, 403 `access_blocked`/`model_blocked`/`provider_blocked`, 429 `token_limited`/`request_limited`, 402 `budget_exceeded`. Storage: SQLite or PostgreSQL; deny-by-default provider access; dashboard supports budget overrides for temporary increases — [Bifrost Virtual Keys docs](https://docs.getbifrost.ai/features/governance/virtual-keys)
- Vendor framing: budgets attach to customer, team, virtual-key and provider-config levels, each checked on every request; "When a budget is exhausted, Bifrost blocks further requests instead of reconciling overspend later." — [Bifrost Governance page](https://www.getmaxim.ai/bifrost/resources/governance); [Maxim article on rate limiting](https://www.getmaxim.ai/articles/llm-api-rate-limiting-with-virtual-keys-and-budgets/)

**Kong AI Gateway**
- AI Rate Limiting Advanced plugin "uses token data returned by the LLM provider to calculate the costs of queries"; configured per `llm_providers` with parallel `limit: [100, 1000]` / `window_size: [60, 3600]` arrays; supports a token-counting strategy for prompt, completion, total tokens or cost; newer `policies` field matches on `consumer` id — [Kong AI Rate Limiting Advanced](https://developer.konghq.com/plugins/ai-rate-limiting-advanced/); [Kong example](https://developer.konghq.com/plugins/ai-rate-limiting-advanced/examples/llm-provider-rate-limiting/); [Kong blog on token rate limiting](https://konghq.com/blog/engineering/token-rate-limiting-and-tiered-access-for-ai-usage)

**OpenRouter (hosted; useful as a reference model)**
- Provisioning API: a Management key creates per-user keys via `/api/v1/keys`; each key carries a spend `limit` and `limit_reset` of `daily`, `weekly`, `monthly` or `null`; resets at midnight UTC, weeks Monday-Sunday; all keys draw from one account balance — [OpenRouter Provisioning API Keys](https://openrouter.ai/docs/features/provisioning-api-keys); [OpenRouter help: one key per user](https://openrouter.zendesk.com/hc/en-us/articles/51680687417499-Can-I-create-one-API-key-per-user-with-its-own-spending-limit-Management-API-keys); [OpenRouter limits (402/429)](https://openrouter.ai/docs/api_reference/limits)

### Inferences
- The consensus schema for a small proxy is: `keys(id, hash, alias, user_id, team_id, models[], expires_at, is_active)`, `budgets(key_or_user_id, max_limit, unit=usd|tokens|requests, reset_duration, calendar_aligned, current_usage, last_reset)`, `spend_logs(ts, key_id, user_id, model, input_tokens, output_tokens, cache_creation_input_tokens, cache_read_input_tokens, cost_usd, request_id, metadata)` — this is a direct synthesis of the LiteLLM and Bifrost fields above.
- Two reset styles appear in practice and both are worth supporting: rolling windows (LiteLLM `budget_duration` measured from key creation/last reset; Bifrost default) and calendar-aligned windows (Portkey weekly/monthly at 00:00 UTC; OpenRouter daily/weekly/monthly at midnight UTC; Bifrost `calendar_aligned`). Claude's own subscription limits are rolling (5 h from first message, 7 days) so a proxy mirroring subscription behaviour should default to rolling windows.
- Status-code conventions differ: LiteLLM returns 400 for budget exhaustion, Bifrost returns 402 `budget_exceeded`, OpenRouter returns 402 for insufficient credits; everyone returns 429 for rate/token-per-window limits. For Claude Code as a client, returning an Anthropic-shaped error body (`{"type":"error","error":{"type":"rate_limit_error","message":...}}`) with 429 is most likely to be surfaced cleanly, but I found no source documenting how Claude Code renders proxy-originated 402s (gap).
- Correct Anthropic streaming accounting: take `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens` from `message_start`, take `output_tokens` from the final `message_delta` (cumulative, so overwrite not add), and if `message_delta.usage` also contains input/cache fields (as in the server-tool example) prefer those as authoritative. Never sum `message_start` and `message_delta` (one-api-pro bug) and never read only `message_delta` (llmio/forge bug). This is inferred from the Anthropic docs plus the bug reports cited above.
- Pre-request enforcement needs an estimate because usage is only known after the stream ends; LiteLLM's "budget reservation" (estimate max cost from `max_tokens` and pricing, reserve, then reconcile) is the reusable pattern for preventing concurrent overspend.
- Only LiteLLM documents the OAuth-forwarding mode; Bifrost, Portkey, Helicone and Kong docs I read describe only provider API keys stored in the gateway. This is an absence of evidence in the pages fetched, not a confirmed incapability.

### Gaps
- I did not find primary documentation for Bifrost's, Portkey's or Helicone's Anthropic SSE parsing logic (their source was not fetched); only LiteLLM's behaviour is documented via issues/PRs.
- Portkey's and Helicone's dashboard panel inventories were not fetched in detail.
- Whether Helicone rate-limit windows are sliding or fixed is not stated in its docs.
- No source found on how LiteLLM prices requests in OAuth pass-through mode (it presumably computes API-equivalent USD from model pricing, but this is unverified).

## Key Question 2: Claude Code usage monitors — data sources, statistics, plan-limit estimation, visualisation libraries

### Takeaway
Two data sources exist: (1) local JSONL transcripts under `~/.claude/projects/` (used by ccusage, Claude-Code-Usage-Monitor, and virtually all web dashboards), which give exact per-message token counts but only for the local machine and require plan limits to be guessed; and (2) the undocumented `GET https://api.anthropic.com/api/oauth/usage` endpoint (Bearer OAuth token + `anthropic-beta: oauth-2025-04-20`), which returns authoritative 5-hour and 7-day utilisation percentages and `resets_at` timestamps but no token counts. Terminal tools use Rich (Python) or ANSI tables (TypeScript); web tools overwhelmingly use Chart.js over SQLite.

### Cited Findings

**ccusage (ryoppippi, TypeScript)**
- Reads local JSONL logs from `~/.claude/projects` (and many other coding-agent CLIs: Codex, OpenCode, Gemini CLI, Copilot CLI, etc.). Report types: daily, weekly, monthly, session, blocks (5-hour billing windows with active-block monitoring), plus a statusline. Statistics: input, output, cache-creation and cache-read tokens, USD cost, per-model breakdown, burn rate, projected usage, token limits for blocks. Deduplicates on `messageId` + `requestId`. Pricing comes from LiteLLM's pricing data (offline-cacheable); cost modes auto/calculate/display; JSON export; timezone-configurable; colored responsive terminal tables — [ccusage README](https://github.com/ryoppippi/ccusage/blob/main/apps/ccusage/README.md)
- Blocks: "triggered by your first message" and "last exactly 5 hours from start time", UTC handling; `--token-limit <n|max>` where `max` uses the highest previous block as the limit; burn rate is tokens per minute within the block plus projected total tokens/cost if the rate continues; progress colours green <70%, yellow 70-90%, red >=90%; `--live` mode was removed in v18 in favour of the statusline — [ccusage Blocks guide](https://ccusage.com/guide/blocks-reports)

**Claude-Code-Usage-Monitor / claude-monitor (Maciek-roboblog, Python)**
- Reads JSONL logs from the Claude config dir (`--data-paths`, `CLAUDE_CONFIG_DIR`); can also capture Claude Code's statusline `rate_limits` via `--statusline`. Plans: Pro ~19,000 tokens, Max5 ~88,000, Max20 ~220,000, and `custom` which auto-detects a limit using the P90 of the last 192 hours of sessions. Models the "5-hour rolling session window" starting from first message, with overlapping sessions; `--reset-hour` aligns to a daily schedule. Displays token consumption (input/output/cache), burn rate (tokens/min), cost, predicted depletion time, message count. Stack: Rich TUI with light/dark auto-theme, Pydantic config, numpy statistics; outputs `--once --output json`, `--write-state`, `--compact`, `--warehouse` (CSV/JSON history). Install `uv tool install claude-monitor` or `pip install claude-monitor` — [Claude-Code-Usage-Monitor README](https://github.com/Maciek-roboblog/Claude-Code-Usage-Monitor)
- Issue #202 documents why JSONL-based estimation is inaccurate: the tool rounds the first local entry's timestamp to the nearest hour + 5 h, so if the first message came from another device the window boundary is wrong, and local files miss other devices' activity entirely ("ccm showed 1.4% while the server showed 12% for the same window") — [Claude-Code-Usage-Monitor Issue #202](https://github.com/Maciek-roboblog/Claude-Code-Usage-Monitor/issues/202)

**Anthropic OAuth usage endpoint (undocumented)**
- `GET https://api.anthropic.com/api/oauth/usage` with `Authorization: Bearer <oauth_access_token>`, `anthropic-beta: oauth-2025-04-20`, and a `User-Agent: claude-code/<version>` (omitting it "triggers aggressive rate limiting"; safe at ~180 s polling with it). Response: `five_hour: {utilization 0-100, resets_at ISO-8601}`, `seven_day: {...}`, `seven_day_opus: null|{...}`, `seven_day_sonnet: null|{...}`, `extra_usage: {is_enabled, monthly_limit, ...}`. Credentials: macOS Keychain (`security find-generic-password -s "Claude Code-credentials" -w`), `~/.claude/.credentials.json` (`claudeAiOauth.accessToken/refreshToken/expiresAt`), or `CLAUDE_CODE_OAUTH_TOKEN`; access tokens expire ~60 min and refresh when Claude Code runs — [Claude-Code-Usage-Monitor Issue #202](https://github.com/Maciek-roboblog/Claude-Code-Usage-Monitor/issues/202)
- The endpoint is described as undocumented and unversioned; its response shape has already changed once, so tools can break silently — [SeaWork blog: Claude Code Usage 2026](https://seawork.ai/en/blogs/claude-code-usage/); implementation example in a third-party GUI PR "plan-limit usage meter (5-hour / weekly windows from the Claude Code OAuth usage API)" — [extropolis/claudia PR #250](https://github.com/extropolis/claudia/pull/250)
- Community observation that the "weekly" window behaved as a ~72-hour reset rather than 7 days at one point — [monperrus gist](https://gist.github.com/monperrus/3ac4b303a84946bbeaf2b1123ee99491) (single anecdotal source; unverified)

**Web dashboards reading JSONL**
- phuryn/claude-usage: Python stdlib only (`sqlite3`, `http.server`), Chart.js from CDN, reads `~/.claude/projects/` JSONL, stores in SQLite at `~/.claude/usage.db` with incremental scanning by path+mtime; shows today/7-day/all-time, per-model tokens and cost, cache write/read, sessions and projects; prices only models whose name contains `fable`, `mythos`, `opus`, `sonnet`, `haiku`; "Pro and Max subscribers get a progress bar" — [phuryn/claude-usage](https://github.com/phuryn/claude-usage)
- AeternaLabsHQ/claude-code-stats: Python stdlib, static HTML dashboard in `public/` with inline JS; shows daily API-equivalent value by model, cumulative cost curves, token breakdown (input/output/cache-read/cache-write), GitHub-style activity heatmap, hourly and weekday message distribution, daily sessions, sortable session table with range sliders (tokens, cost, duration, tool calls, agent dispatches, errors), per-tool output tokens/cost, cache health (idle-gap overhead, "no-gap flush events"), and reconciles API-equivalent cost against subscription spend to compute savings/ROI per billing cycle; multi-user/multi-machine merge via config — [AeternaLabsHQ/claude-code-stats](https://github.com/AeternaLabsHQ/claude-code-stats)
- jeremyeder/ccusage-graphs: consumes ccusage JSON exports, SQLite (`daily_usage`, `model_usage` tables), HTML dashboard with Chart.js 4.4.1 (offline, embedded data) plus Grafana dashboards (JSON and SQLite datasource), optional Docker stack of Prometheus 2.48, Grafana 10.2, JSON Exporter, nginx; charts include daily token trends, cost by model, cache efficiency (hit rate, tokens cached/read) — [jeremyeder/ccusage-graphs](https://github.com/jeremyeder/ccusage-graphs)
- Others found (not fetched in depth): Genius-Cai/claude-usage-dashboard (Next.js 14 + FastAPI + PWA) — [repo](https://github.com/Genius-Cai/claude-usage-dashboard); tanu360/claude-code-dashboard (Next.js) — [repo](https://github.com/tanu360/claude-code-dashboard); developer-hasm/claude-code-dashboard (Next.js, served as a Claude Code plugin; monitors rate limits, daily activity, usage rankings) — [repo](https://github.com/developer-hasm/claude-code-dashboard); yahav10/claude-code-dashboard ("Claude Code Insights", local-first, zero telemetry) — [repo](https://github.com/yahav10/claude-code-dashboard); "Claude Observatory" (Next.js, indexes `~/.claude/` into SQLite, bound to 127.0.0.1) — [DEV Community post](https://dev.to/creative_brain_inc/i-built-a-local-first-dashboard-for-everything-claude-code-does-on-my-machine-133g)

**OpenTelemetry route (official Claude Code telemetry)**
- Claude Code exports OTLP metrics when `CLAUDE_CODE_ENABLE_TELEMETRY=1` and `OTEL_EXPORTER_OTLP_ENDPOINT` are set (`OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE=cumulative` recommended). Metric names in Prometheus form: `claude_code_session_count_total`, `claude_code_token_usage_tokens_total`, `claude_code_cost_usage_USD_total`, `claude_code_active_time_seconds_total`, `claude_code_lines_of_code_count_total`, `claude_code_commit_count_total`, `claude_code_pull_request_count_total`, `claude_code_code_edit_tool_decision_total`; labels include `organization_id`, `user_email`, `model`, `session_id`, `terminal_type`, `type` (token category), `language`, `decision`, `query_source`, `effort` — [Grafana dashboard 25255 "Claude Code Metrics (Prometheus)"](https://grafana.com/grafana/dashboards/25255-claude-code-metrics-prometheus/)
- Grafana dashboard 25255 panels: overview KPIs (sessions, users, total cost, tokens, commits, PRs, lines added/removed, active time, tokens by type, tool decisions); leaderboards (top users by cost/tokens, top sessions by cost, cost by model, edit decisions by language, sessions by terminal); cost and token trends by model; active time and LoC per hour; cost by query source and effort; cache hit ratio — [Grafana 25255](https://grafana.com/grafana/dashboards/25255-claude-code-metrics-prometheus/); related dashboards [24993](https://grafana.com/grafana/dashboards/24993-claude-code-metrics/), [25052](https://grafana.com/grafana/dashboards/25052-claude-code/), [24640 VictoriaStack](https://grafana.com/grafana/dashboards/24640-claude-code-victoriastack/); setup guides [Quesma blog](https://quesma.com/blog/track-claude-code-usage-and-limits-with-grafana-cloud/), [Sealos blog](https://sealos.io/blog/claude-code-metrics/)

### Inferences
- A proxy is positioned between the two data sources: like JSONL tools it sees exact per-request token counts (from the SSE stream), but unlike them it sees every device/user that routes through it, and it could additionally poll `/api/oauth/usage` with the shared account's token to display authoritative 5-hour/7-day utilisation next to per-user metering. The token-limit tables in claude-monitor (Pro ~19k, Max5 ~88k, Max20 ~220k) are heuristics, not published Anthropic numbers, and should not be hard-coded as truth.
- The P90-of-recent-blocks heuristic (claude-monitor `custom` plan) and ccusage's `--token-limit max` (highest past block) are the two common ways to infer a plan ceiling from history; both are reasonable fallbacks when the OAuth endpoint is unavailable.
- The 5-hour block algorithm shared by ccusage and claude-monitor (start at the hour-floor of the first message, end +5 h, new block after a gap past expiry) is a reusable, simple approach for a proxy's per-user "session window" view.
- The OAuth usage endpoint needs the correct `User-Agent` and a refresh strategy; since Claude Code refreshes the token itself, a proxy that forwards live Claude Code requests can opportunistically capture the freshest bearer token from incoming requests rather than managing refresh (inference; no source describes this).

### Gaps
- I did not find Anthropic documentation for the exact plan token/message allowances behind the 5-hour and weekly windows; all numbers in the wild are estimates.
- I did not verify current ccusage version details (e.g. whether cache tokens count toward block totals); the blocks guide does not state it.
- I did not fetch the Next.js dashboards' READMEs (Genius-Cai, tanu360, developer-hasm) so their chart libraries are unknown.

## Key Question 3: Which dashboard statistics are conventional for this domain?

### Takeaway
Across gateways (LiteLLM UI, Grafana Claude Code dashboards) and local monitors (ccusage, claude-monitor, claude-code-stats), the recurring panel set is: KPI tiles (total cost, tokens, requests/sessions, users), time-series of tokens and cost by day/week/month split by model and by token type, cache metrics (cache-read vs cache-creation tokens, cache hit ratio), leaderboards (top users/keys/sessions by cost or tokens), activity heatmaps (day-of-week x hour, GitHub-style calendar), and for the active window: progress bar against a limit, burn rate (tokens/min), and projected exhaustion/depletion time.

### Cited Findings
- Gateway dashboard (LiteLLM Usage tab): spend by model, API key, team, tag; daily spend trend chart; spend per internal user and customer; filtering and export — [LiteLLM Spend Tracking](https://docs.litellm.ai/docs/proxy/cost_tracking)
- Grafana Claude Code dashboard: KPIs (sessions, users, cost, tokens, commits, PRs, LoC, active time, tokens by type, tool decisions), leaderboards (top users by cost/tokens, top sessions by cost, cost by model), cost/token trends by model, cache hit ratio, cost by query source and effort — [Grafana 25255](https://grafana.com/grafana/dashboards/25255-claude-code-metrics-prometheus/)
- ccusage: daily/weekly/monthly/session/blocks tables with input, output, cache-create, cache-read, cost, per-model breakdown; blocks add burn rate (tokens/min), projected total tokens/cost, token-limit progress with 70%/90% colour thresholds — [ccusage README](https://github.com/ryoppippi/ccusage/blob/main/apps/ccusage/README.md); [ccusage blocks guide](https://ccusage.com/guide/blocks-reports)
- claude-monitor: token consumption, burn rate tokens/min, cost, predicted depletion time, message count, plan progress against Pro/Max5/Max20/custom limit — [Claude-Code-Usage-Monitor README](https://github.com/Maciek-roboblog/Claude-Code-Usage-Monitor)
- claude-code-stats: daily API value by model, cumulative cost curve, token breakdown, GitHub-style activity heatmap, hourly and weekday distribution, daily sessions, sortable session table, per-tool cost, cache health, subscription ROI (API-equivalent value vs subscription price) — [AeternaLabsHQ/claude-code-stats](https://github.com/AeternaLabsHQ/claude-code-stats)
- ccusage-graphs: daily token trends, cost by model, cache efficiency (hit rate, tokens cached/read), historical time-series — [jeremyeder/ccusage-graphs](https://github.com/jeremyeder/ccusage-graphs)
- The official OAuth endpoint exposes only utilisation % and `resets_at` for 5-hour, 7-day, and per-model-family 7-day windows — the "official" statistics Claude Code's `/usage` shows — [Issue #202](https://github.com/Maciek-roboblog/Claude-Code-Usage-Monitor/issues/202)

### Inferences
- "Cache hit ratio" is conventionally `cache_read_input_tokens / (input_tokens + cache_creation_input_tokens + cache_read_input_tokens)`; the Grafana dashboard and ccusage-graphs both surface it, but I did not find a single canonical formula in the sources, so the definition should be stated explicitly in any dashboard.
- "Cost equivalent" for subscription users means API-list-price cost computed from the LiteLLM pricing table (ccusage) or an embedded pricing table (claude-code-stats, phuryn/claude-usage); the claude-code-stats ROI panel (API value vs subscription fee) is a distinctive, borrowable idea for a shared-subscription proxy.
- For an admin of a shared-account proxy, the most decision-relevant additions over the single-user tools are: per-user leaderboards, per-user budget progress bars with reset countdowns, and an account-level "official utilisation" gauge from the OAuth endpoint so the admin can see how close the shared account is to being throttled.

### Gaps
- No survey/benchmark source ranks which statistics users find most valuable; the list above is an inventory of what shipped tools show.

## Key Question 4: Which lightweight stacks are common, with pros/cons for a small self-hosted tool?

### Takeaway
The dominant patterns in this niche are (1) a single Python process (stdlib `http.server` or FastAPI) serving a Chart.js single-page dashboard over SQLite, (2) Next.js + SQLite local apps, and (3) the OpenTelemetry -> Prometheus -> Grafana stack for team/enterprise monitoring. Streamlit shows up in general dashboard comparisons but not in any Claude Code tool I found; Grafana is favoured when alerting and non-developer panel editing matter, at the cost of running extra services.

### Cited Findings
- Python stdlib + SQLite + Chart.js (CDN), no dependencies: phuryn/claude-usage — [repo](https://github.com/phuryn/claude-usage); Python stdlib + static HTML with inline JS: claude-code-stats — [repo](https://github.com/AeternaLabsHQ/claude-code-stats); SQLite + Chart.js 4.4.1 HTML plus optional Prometheus/Grafana/nginx Docker stack: ccusage-graphs — [repo](https://github.com/jeremyeder/ccusage-graphs)
- Next.js 14 + FastAPI + PWA: Genius-Cai/claude-usage-dashboard — [repo](https://github.com/Genius-Cai/claude-usage-dashboard); Next.js + SQLite local-first: Claude Observatory — [DEV post](https://dev.to/creative_brain_inc/i-built-a-local-first-dashboard-for-everything-claude-code-does-on-my-machine-133g); Next.js served as a Claude Code plugin — [developer-hasm/claude-code-dashboard](https://github.com/developer-hasm/claude-code-dashboard)
- OTLP -> Prometheus/VictoriaMetrics/Mimir/Thanos -> Grafana 11+: [Grafana 25255](https://grafana.com/grafana/dashboards/25255-claude-code-metrics-prometheus/); guides [Quesma](https://quesma.com/blog/track-claude-code-usage-and-limits-with-grafana-cloud/), [Sealos](https://sealos.io/blog/claude-code-metrics/)
- Terminal TUIs: Rich (Python) in claude-monitor — [README](https://github.com/Maciek-roboblog/Claude-Code-Usage-Monitor); TypeScript colored tables in ccusage — [README](https://github.com/ryoppippi/ccusage/blob/main/apps/ccusage/README.md)
- Gateways themselves: LiteLLM ships a bundled Admin UI with a Usage tab backed by Postgres — [LiteLLM Spend Tracking](https://docs.litellm.ai/docs/proxy/cost_tracking); Bifrost ships a dashboard backed by SQLite or PostgreSQL — [Bifrost Virtual Keys](https://docs.getbifrost.ai/features/governance/virtual-keys)
- Streamlit vs Grafana (general comparison): "Use Streamlit for quick, Python-powered apps and ML monitoring, and Grafana for scalable, alert-driven infrastructure and metrics tracking"; Grafana panels are editable by non-developers via UI/JSON while Streamlit apps are Python scripts needing a coder to maintain — [Fastero: Streamlit vs Grafana](https://fastero.com/blog/streamlit-vs-grafana-when-to-use-each); [Visivo comparison](https://visivo.io/comparisons/streamlit-grafana)

### Inferences
- For a small self-hosted proxy whose core is already an HTTP server, the lowest-friction choice mirrored by the field is: the proxy process (FastAPI/Starlette or equivalent) writes `spend_logs` to SQLite and serves a static HTML page using Chart.js (or ECharts/Plotly) that fetches JSON aggregates from a few endpoints. Pros: one process, one file DB, no build step, offline. Cons: no alerting, hand-rolled auth for the admin UI.
- Grafana + Prometheus (or Grafana with a SQLite datasource, as ccusage-graphs does) is preferable when several people already run Grafana or when alerting on budget thresholds is wanted; the cost is 2-3 extra containers and Prometheus's poor fit for per-request logs (it stores aggregates, not rows; leaderboards by user require label cardinality).
- Streamlit is fast to write but re-runs the script per interaction and is awkward to embed in a proxy process; none of the surveyed Claude Code tools chose it, which weakly suggests a poor fit for an always-on admin dashboard.
- Next.js is chosen by tools that want a richer UI (session browsers, agent management) and is over-scoped for a metering dashboard unless the team already works in TypeScript.
- A reusable-component shortcut: emit Claude Code-compatible OTel metrics (`claude_code.token.usage` with `type` label, `claude_code.cost.usage`, `user_email` label) from the proxy so the existing Grafana dashboards (25255/24993/25052) work unchanged; this is an inference from the metric/label list, not something any source demonstrates.

### Gaps
- No source found directly comparing FastAPI+Chart.js vs Streamlit vs Grafana specifically for LLM usage dashboards; the comparison above is synthesised from the tools' own stacks and generic Streamlit/Grafana articles.
- ECharts and Plotly usage in this niche was not observed in the fetched repos (Chart.js dominated); absence may reflect the sample, not the ecosystem.
