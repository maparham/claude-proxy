# One proxy already does it, nobody does share-of-quota

Exactly one open-source project matches the full brief of a transparent `ANTHROPIC_BASE_URL` proxy for genuine Claude Code clients with per-user token accounting, admin-set per-user limits and a dashboard: **devasheeshG/claude-code-proxy** (FastAPI + Next.js + PostgreSQL), which has 0 stars and whose author says it is unreviewed "vibe-coded" code despite handling **20 billion tokens and about 70,000 requests** in internal use ([devasheeshG README](https://github.com/devasheeshG/claude-code-proxy)). The two largest functional matches are the Chinese "carpool" gateways **Wei-Shaw/claude-relay-service (12,633 stars)** and **Wei-Shaw/sub2api (42,134 stars)**, both built explicitly for "3-5 friends splitting a Max subscription" with per-person keys, per-key token/request limits and admin UIs ([claude-relay-service](https://github.com/Wei-Shaw/claude-relay-service); [sub2api](https://github.com/Wei-Shaw/sub2api)). The English-language multi-account proxies **teamclaude (335 stars)** and **dario (542 stars)** are the best-engineered references for OAuth handling, SSE usage parsing and rate-limit semantics, but both deliberately stop at per-key *attribution* and ship no per-user limits ([dario docs/keys.md](https://github.com/askalf/dario/blob/master/docs/keys.md)). No surveyed project implements the second limit type in the brief, a per-user *share of the account's 5-hour/7-day quota*; every one that reads Anthropic's utilization signal uses it only for account rotation, and dario names per-key share-of-window quotas as "the obvious next step" that is "deliberately not in this version". The technical substrate is well mapped but entirely undocumented: a hard-coded client ID, single-use rotating refresh tokens, an `anthropic-beta: oauth-2025-04-20` header, a `claude-cli` User-Agent, and an undocumented `GET /api/oauth/usage` endpoint that returns whole-percent 5h/7d utilization and is rate-limited per token. The policy picture is unambiguous and adverse: Anthropic's Claude Code legal page says developers "may not collect, store, or intermediate Claude.ai credentials or session tokens" or "route requests through Free, Pro, or Max plan credentials on behalf of their users", the Consumer Terms forbid making an account "available to anyone else", and enforcement has escalated since January 2026 from server-side blocking to a legal demand against OpenCode ([Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance); [Consumer Terms](https://www.anthropic.com/legal/consumer-terms)). The projects' own consensus is that sharing one account across distinct people is "the clear violation"; the sanctioned alternatives are Claude for Teams seats ($20-25/seat/month) or a Console API key behind a LiteLLM-style gateway.

## Three architectures compete and only one is a drop-in for Claude Code

The design space splits into three shapes, and the choice determines whether the Claude Code CLI can be served at all. The first is the **transparent proxy**: the client sets `ANTHROPIC_BASE_URL` and an `ANTHROPIC_AUTH_TOKEN` that is really a proxy-issued virtual key; the proxy swaps in the pool's OAuth bearer and forwards the request otherwise byte-for-byte. dario describes the discipline precisely: "A genuine Claude Code request already *is* the Claude Code shape, so dario forwards it byte-for-byte — system prompt, tools, thinking, key order untouched — swapping in only the pool's credential, its billing tag and cache breakpoints" ([dario README](https://github.com/askalf/dario)). devasheeshG, teamclaude, maxpool, dario, CC-Router, claude-relay-service and sub2api all take this shape. The second shape is the **CLI subprocess wrapper** (ocp, wende/claude-max-api-proxy, thhuang's Rust port, RichardAtCT's wrapper, ai-cli-bridge): it spawns `claude -p --output-format stream-json` and exposes an OpenAI-compatible API, so that "Anthropic sees normal Claude Code usage" ([ocp README](https://github.com/dtzp555-max/ocp)). These serve *other* clients (Aider, OpenCode, chat UIs) and cannot sit in front of a Claude Code user, which rules them out for this brief even though ocp and ai-cli-bridge do have per-key limits and dashboards. The third shape is **client-side enforcement**: howincodes/claude-code-limiter installs root-owned managed-settings hooks (`UserPromptSubmit` as "THE GATE", `Stop` to increment usage) that call a self-hosted Express/SQLite server on every prompt; it counts **turns, not tokens** ("We count **turns** (user prompts), not individual tool calls") and never sees the API traffic ([claude-code-limiter README](https://github.com/howincodes/claude-code-limiter)). It has 53 stars, was last pushed 2026-03-25, is marked "Early Beta", still has a "Screenshot placeholder" in its README, and its Docker image shipped without the dashboard build (`Cannot GET /dashboard`) ([issue #3](https://github.com/howincodes/claude-code-limiter/issues/3)).

devasheeshG's implementation is the most instructive because its code is readable in detail. Its enforcement is pre-request from ledgers: per-user `rate_limit_per_minute` raises HTTP 429, while `monthly_token_budget`, `lifetime_token_budget`, `monthly_spend_budget_usd` and `lifetime_spend_budget_usd` raise HTTP **403** with messages such as "User monthly token budget exhausted." ([proxy.py](https://github.com/devasheeshG/claude-code-proxy/blob/main/backend/app/routes/proxy.py)). It records `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens` and the nested 5-minute versus 1-hour `cache_creation` buckets per model, user, key and account, with estimated USD from a pricing table where "Unknown models have no pricing entry and therefore have an estimated cost of zero" ([usage.py](https://github.com/devasheeshG/claude-code-proxy/blob/main/backend/app/utils/usage.py)). It also synthesises pool-level `anthropic-ratelimit-unified-5h-utilization`, `-7d-utilization`, `-reset` and `-status` response headers plus a `GET /api/v1/me/usage` endpoint so that Claude Code's `/usage` and statusline show pooled numbers "rather than reporting whichever account answered last" ([README](https://github.com/devasheeshG/claude-code-proxy)). A consequence worth noting for the target design: because budgets are checked against historical totals before forwarding, the request that crosses a budget is still served in full; none of the surveyed projects cut a stream off mid-flight.

A distinct, sanctioned-adjacent option is **LiteLLM's OAuth pass-through mode**. Its official tutorial has Claude Code keep its *own* login and send the OAuth bearer in `Authorization`, while a LiteLLM virtual key travels in `ANTHROPIC_CUSTOM_HEADERS="x-litellm-api-key: Bearer <virtual_key>"`; with `forward_client_headers_to_llm_api: true` the OAuth token is forwarded and the virtual key drives auth, logging and budgets ([LiteLLM tutorial](https://docs.litellm.ai/docs/tutorials/claude_code_max_subscription)). The maintainer frames this as "LiteLLM doesn't replace or store your subscription as an API key. It acts as a proxy that forwards the authenticated Claude Code request" ([Discussion #20072](https://github.com/BerriAI/litellm/discussions/20072)). This gives per-key budgets and the LiteLLM Usage UI for free, but it is a one-login-per-user pattern: each user still authenticates with their own subscription, so it meters but does not *share* a single account. It also has a live bug where LiteLLM validates the `sk-ant-oat-*` bearer as its own key and returns 401 when both headers are present ([Issue #29190](https://github.com/BerriAI/litellm/issues/29190)).

## Share-of-account limits do not exist because the signal is too coarse

The brief asks for two limit types: absolute tokens per window, and a share of the account's quota. The first is commodity; the gateway field has converged on one schema. LiteLLM attaches to a virtual key `max_budget`, `budget_duration` (`30s`…`30d`, `1mo`, `7d` resetting Sundays UTC), `tpm_limit`, `rpm_limit`, `max_parallel_requests`, and supports multiple concurrent windows on one key (`[{"budget_duration": "24h", "max_budget": 10}, {"budget_duration": "30d", "max_budget": 100}]`), enforced pre-request with a "budget reservation" that estimates maximum cost from `max_tokens`, reserves it, and reconciles after the response ([LiteLLM Budgets docs](https://docs.litellm.ai/docs/proxy/users)). Bifrost's budget object adds `reset_duration` (`1m`…`1Y`) and a `calendar_aligned` flag to choose UTC-boundary resets over rolling windows, and returns 402 `budget_exceeded` versus 429 `token_limited`/`request_limited` ([Bifrost Virtual Keys](https://docs.getbifrost.ai/features/governance/virtual-keys)). Status codes are inconsistent across the field (LiteLLM 400, Bifrost and OpenRouter 402, devasheeshG 403, ocp 429), and no source documents how Claude Code renders a proxy-originated 402, so an Anthropic-shaped `rate_limit_error` body with 429 is the safest guess. Because Claude's own limits are rolling (5 hours from first message, 7 days), a proxy mirroring subscription behaviour should default to rolling windows; ccusage's block algorithm (floor the first message to the hour, end at +5 h, new block after a gap past expiry) is the reusable model for a per-user "session window" view ([ccusage blocks guide](https://ccusage.com/guide/blocks-reports)).

The second limit type is where the field is empty. **No surveyed project converts Anthropic's per-account 5-hour/7-day utilization into a per-user share or enforces a per-user percentage of the account's quota.** teamclaude has the closest mechanism, but at account granularity only: `accounts[].maxUsage` accepts "a number, or a per-bucket table like `{ "unified7d": 0.6, "unified7dFable": 0.8 }`", while per-client keys only book tokens ("the tokens its responses report are booked against `name`") with no cap ([teamclaude docs/configuration.md](https://github.com/KarpelesLab/teamclaude/blob/main/docs/configuration.md)). claude-code-limiter approximates cost weighting with admin-set credits per prompt ("opus costs 10, sonnet costs 3, haiku costs 1"), not a measured share ([README](https://github.com/howincodes/claude-code-limiter)). ocp caps requests per key and simply notes "All users share your Claude Pro/Max **rate limits** (5h session + 7d weekly)" ([ocp lan-mode.md](https://github.com/dtzp555-max/ocp/blob/main/docs/lan-mode.md)).

The reasons are structural. The utilization signal arrives on every response as headers such as `anthropic-ratelimit-unified-5h-utilization: 0.38`, `anthropic-ratelimit-unified-7d-utilization: 0.81`, `anthropic-ratelimit-unified-representative-claim: seven_day` and `anthropic-ratelimit-unified-fallback-percentage: 0.5` ([dario discussion #1](https://github.com/askalf/dario/discussions/1)), but the OAuth utilization "arrives on a whole-percent grid" ([teamclaude docs/configuration.md](https://github.com/KarpelesLab/teamclaude/blob/main/docs/configuration.md)), there are separate per-model weekly buckets (`7d_<family>`, tracked by both dario and teamclaude), concurrent requests from several users land between header readings, and cache reads and cache creation count differently. Attributing the *delta* in a whole-percent gauge to the user whose request moved it is therefore noisy at best for 2-3 concurrent users, and no Anthropic documentation of how utilization is computed from tokens per model was found. The practical design that falls out of this is the one the ChatGPT summary also lands on (see below): keep three quantities strictly separate, namely the account's official utilization from headers or the usage endpoint, each user's observed tokens from the SSE stream, and each user's admin-set allocation; then express "share of quota" as an admin-configured fraction applied to the account's utilization headroom (for example, "Alice may consume until the account's 7d gauge has moved 40 points attributable to her since reset"), labelled explicitly as an estimate, with token-weighted apportionment as the attribution heuristic.

## The credential plumbing is reverse-engineered and refresh tokens are single-use

Everything needed to hold a subscription credential outside the CLI is community-documented and nothing is official. Anthropic documents only *where* credentials live: the macOS Keychain (falling back to `~/.claude/.credentials.json` mode 0600 when the Keychain is locked, as over SSH), `~/.claude/.credentials.json` on Linux, and `CLAUDE_CONFIG_DIR` to relocate it, adding that to route through a custom endpoint one should use `ANTHROPIC_BASE_URL` rather than hand-manage the file ([Authentication docs](https://code.claude.com/docs/en/authentication)). The reverse-engineered parts, extracted from the CLI binary, are a hard-coded client ID `9d1c250a-e61b-44d9-88ed-5944d1962f5e`, authorize URL `https://claude.ai/oauth/authorize`, token endpoint `https://platform.claude.com/v1/oauth/token`, PKCE S256, and tokens prefixed `sk-ant-oat01-` (access) and `sk-ant-ort01-` (refresh) with `expires_in: 28800` ([shubcodes gist](https://gist.github.com/shubcodes/3c9c7ff813715aa47018bf22e7cf8cb5)). devasheeshG's config confirms the same client ID and endpoints and uses a wider scope string including `user:inference user:sessions:claude_code user:mcp_servers user:file_upload` ([config.py](https://github.com/devasheeshG/claude-code-proxy/blob/main/backend/app/config.py)). Access-token TTL reports conflict across sources (8 hours in the gist, "~60 minutes" in Claude-Code-Usage-Monitor #202, 8-24 hours in claude-code issues), so treat it as variable and refresh on the `expiresAt` field rather than a constant.

The single most repeated pitfall is **refresh-token rotation**. dario: "Refresh tokens are single-use, so two replicas refreshing the same seat leave one holding a dead token" ([dario README](https://github.com/askalf/dario)); tokengateway: multiple refreshers cause "race conditions and premature auth invalidation (`400 invalid_grant`)" ([tokengateway README](https://github.com/eduardopessin/tokengateway)); maxpool removed import of the CLI's own login entirely because "it shares a single-use credential the CLI keeps rotating, which broke the pooled copy. Use browser login so maxpool holds its own independent grant" ([maxpool README](https://github.com/2solarmax/maxpool)). Upstream Claude Code issues show the same failure when Claude Desktop's embedded CLI and the terminal CLI share one Keychain entry, producing daily "Login expired" ([claude-code #94464](https://github.com/anthropics/claude-code/issues/94464)). The design consequence is firm: the proxy must complete its own browser OAuth grant, be the sole refresher of that grant, and serialise refreshes (devasheeshG: "serialized refresh-token rotation and reauthentication detection"). Requests then need `Authorization: Bearer <token>`, `anthropic-beta: oauth-2025-04-20` ("required for subscription tokens") and a Claude Code User-Agent (`claude-cli/1.0.60 (external, cli)` in devasheeshG, described as keeping OAuth requests "out of the aggressively rate-limited bucket") ([config.py](https://github.com/devasheeshG/claude-code-proxy/blob/main/backend/app/config.py)), and the body's `account_uuid` must be rewritten to match the injected token ([teamclaude README](https://github.com/KarpelesLab/teamclaude)). dario's drift log shows that these fingerprints move: `context-1m` was dropped from the default OAuth beta set, and "Per-model `anthropic-beta` sets — Proxies sending one set diverge for non-Opus models", which is why dario captures the wire shape "live from your own installed `claude` binary on every startup" ([dario README](https://github.com/askalf/dario)). No project mentions cryptographic request signing; auth is bearer token plus headers.

### The usage endpoint gives percentages, not tokens, and throttles per token

The endpoint behind Claude Code's `/usage` is `GET https://api.anthropic.com/api/oauth/usage`, requiring the same bearer, beta header and User-Agent plus the `user:profile` scope. A capture from April 2026 shows the shape: `five_hour` and `seven_day` objects with `utilization` (0-100) and ISO-8601 `resets_at`, nullable `seven_day_opus`/`seven_day_sonnet`, and an `extra_usage` object with `is_enabled`, `monthly_limit`, `used_credits` ([Claude-Code-Usage-Monitor #202](https://github.com/Maciek-roboblog/Claude-Code-Usage-Monitor/issues/202)). It is rate-limited **per access token** with a 429 body `{"error":{"message":"Rate limited. Please try again later.","type":"rate_limit_error"}}` and no `Retry-After`; one reporter saw 429s persist for over 30 minutes, and the Claude Code issue was closed as not a bug with no Anthropic response ([claude-code #31637](https://github.com/anthropics/claude-code/issues/31637)). The community-safe cadence is a 180-second TTL cache with exponential backoff; devasheeshG's default `QUOTA_REFRESH_INTERVAL_SECONDS` is 60 ([config.py](https://github.com/devasheeshG/claude-code-proxy/blob/main/backend/app/config.py)). Two normalisation traps are documented: devasheeshG's code comments record a prior bug where a `> 1.0` heuristic "wrongly read a true 1% as 100%", and its normaliser tolerates `utilization`/`used_percentage` and `resets_at`/`reset_at`/`reset` variants, implying the schema has already shifted ([oauth.py](https://github.com/devasheeshG/claude-code-proxy/blob/main/backend/app/utils/oauth.py)). Since the same utilization also rides on every inference response as `anthropic-ratelimit-unified-*` headers, a proxy can record it per response and reserve polling for idle periods, which sidesteps the per-token 429 bucket that Claude Code itself is drawing from. Anthropic's own client tolerates failures by showing "last-known usage" from the past 60 minutes when the endpoint is throttled ([Manage costs docs](https://code.claude.com/docs/en/costs)).

### Streaming usage must be read from two events and never summed

Anthropic's streaming spec is the primary source for metering: `message_start` carries `message.usage` with `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens` and a placeholder `output_tokens`; `message_delta` carries the final usage, and the docs warn "The token counts shown in the usage field of the message_delta event are cumulative" ([Anthropic Streaming Messages](https://platform.claude.com/docs/en/docs/build-with-claude/streaming)). The correct rule, distilled from devasheeshG's accumulator ("message_delta carries the authoritative final output_tokens; take the latest reported") and from a run of bugs in other proxies, is: take input and both cache counts from `message_start`, overwrite `output_tokens` with the latest `message_delta`, and prefer input/cache fields from `message_delta` if present. one-api-pro double-counted by summing both events, llmio and forge read only `message_delta` and dropped input and cache tokens, and LiteLLM's bridge emitted `input_tokens: 0` in `message_start` ([one-api-pro #13](https://github.com/modelbus/one-api-pro/issues/13); [llmio #71](https://github.com/atopos31/llmio/issues/71); [LiteLLM #41406](https://github.com/BerriAI/litellm/issues/41406)). Cache tokens are not optional: "a sum of `input_tokens` and `output_tokens` understates a cached Claude Code session by orders of magnitude" ([teamclaude docs/configuration.md](https://github.com/KarpelesLab/teamclaude/blob/main/docs/configuration.md)). The parser must be bounded: teamclaude #341 was an "SSE usage-parser [that] accumulates an unbounded string when an upstream stream has no blank line — multi-GB RSS and an uncatchable OOM abort" ([teamclaude #341](https://github.com/KarpelesLab/teamclaude/issues/341)). Every project meters while forwarding rather than buffering, which is also why per-user token limits can only be enforced pre-request from history or an estimate.

### API-mode Claude Code loses the subscription UI, and the statusline is the fix

Pointing Claude Code at a proxy with `ANTHROPIC_AUTH_TOKEN` changes the client's behaviour in documented ways. Credential precedence is cloud provider, then `ANTHROPIC_AUTH_TOKEN` (sent as `Authorization: Bearer`, described as for "an LLM gateway or proxy that authenticates with bearer tokens"), then `ANTHROPIC_API_KEY` (as `X-Api-Key`), then `apiKeyHelper`, `CLAUDE_CODE_OAUTH_TOKEN`, Anthropic profile, and finally `/login` OAuth ([Authentication docs](https://code.claude.com/docs/en/authentication)). In bearer mode the subscription-only surfaces vanish: the statusline `rate_limits` object is present "only for claude.ai Pro and Max subscribers … and only after the first API response in the session" ([Statusline docs](https://code.claude.com/docs/en/statusline)), `/usage-credits` "isn't available with API key authentication", the login-expiry warning is suppressed, and claude.ai connectors and `/schedule` need the claude.ai login. The `/usage` Session block instead computes dollars locally at list price and compares them against `--max-budget-usd` ([Manage costs](https://code.claude.com/docs/en/costs)). This is why devasheeshG bothers to synthesise `anthropic-ratelimit-unified-*` headers: whether Claude Code populates plan bars from those headers when a bearer token is in use is not documented, and the note explicitly flags this as unverified. teamclaude also warns that Claude Code's own OAuth refresh calls to `/v1/oauth/token` are relayed untouched and that "Base-URL mode fails before reaching proxy when local Claude OAuth expires" ([teamclaude #395](https://github.com/KarpelesLab/teamclaude/issues/395)), so users may still need a valid local login even when the proxy supplies the upstream credential.

The reliable channel for showing a proxy user their own allowance is the statusline. It runs an arbitrary command, receives JSON on stdin including `model`, `cost`, `context_window` and (for subscribers) `rate_limits.{five_hour,seven_day,spend_limit}.{used_percentage,resets_at}` with `resets_at` in epoch **seconds** (unlike the raw endpoint's ISO strings), debounces at 300 ms, supports `refreshInterval` (minimum 1 s) for "externally-sourced segments", and re-fires when a window's `resets_at` passes ([Statusline docs](https://code.claude.com/docs/en/statusline)). The docs' own pattern for slow external data is to cache to a temp file and refresh on a timer, so a proxy can expose a small per-user `/me/usage` endpoint that the script polls with `jq`. Anthropic's own Claude apps gateway is the only documented way to inject `rate_limits.spend_limit` values (v2.1.251+); whether a third-party gateway can populate that field is undocumented.

## Rotation, 429 semantics and cache scoping are the hidden operating costs

Beyond credentials and parsing, the surveyed issue trackers converge on a handful of operational lessons that any new proxy should adopt on day one. A 429 has at least three meanings: "A **quota rejection** (a spent 5h or weekly bucket, `unified-…-status: rejected`) switches accounts immediately. A **rate-limit 429** (the per-minute throttle) does **not** switch... A **request-scoped 429** — no `retry-after` and no `anthropic-ratelimit-*` headers at all, which is how upstream refuses a model id it will not serve — is about the request, not the account" ([teamclaude docs/routing.md](https://github.com/KarpelesLab/teamclaude/blob/main/docs/routing.md)); conflating them caused a fleet-wide stall in teamclaude #288. A 403 with `oauth_not_allowed_for_organization` means the org disallows OAuth. `fallback-percentage: 0.5` "means only 50% of capacity is available. In practice, this means Opus and Sonnet return 429 while Haiku keeps working" ([dario discussion #1](https://github.com/askalf/dario/discussions/1)). Failover must happen before the first byte, because once "bytes were on the wire, so the socket reset... ended the stream where they happened, with no `message_stop`, and the client threw away every word it already had" ([dario README](https://github.com/askalf/dario)); maxpool instead queues requests and sends SSE heartbeats "preventing Claude Code's client timeout from abandoning temporary waits" ([maxpool README](https://github.com/2solarmax/maxpool)).

Prompt caching is the largest silent multiplier for a shared account. "The prompt cache is scoped to the account/organization that created it and expires after a few minutes, so the first turn after a switch is a cache **miss**", and stickiness must pin *conversations* rather than client sessions because "Claude Code sends the same session id for its own turns and for every subagent it launches" ([teamclaude docs/routing.md](https://github.com/KarpelesLab/teamclaude/blob/main/docs/routing.md)); dario estimates a lost cache as a "**5-10× token-cost multiplier**" and both dario and devasheeshG expose a switch to force the 1-hour cache TTL ([dario README](https://github.com/askalf/dario)). For a single-account 2-3 user proxy this is less of a routing problem and more of a metering caveat: a user's `cache_read_input_tokens` depend on what the *other* users just sent, which is one more reason per-user "share of quota" can only be an estimate. Transport matters too: Node's global `fetch` multiplexes everything to `api.anthropic.com` over one HTTP/2 connection, and "under many concurrent large uploads (Claude Code POSTs ~1 MB of context per turn) that one connection serializes... and a trivial request can wait minutes for headers" ([teamclaude docs/configuration.md](https://github.com/KarpelesLab/teamclaude/blob/main/docs/configuration.md)). Nginx in front drops headers with underscores such as `session_id`, breaking sticky routing ([sub2api README](https://github.com/Wei-Shaw/sub2api)).

Security bugs in these proxies cluster around admin surfaces and credential leakage: a loopback auth exemption "granted to the whole internet behind a same-host reverse proxy" (#324), "A mistyped /teamclaude/ path is forwarded upstream with an account credential" (#420), a WebSocket upgrade handler "registered outside the API-key gate" (#314) ([teamclaude issues](https://github.com/KarpelesLab/teamclaude/issues?q=is%3Aissue)), and tokengateway's own critical finding that its credential endpoints "have **no authentication**" ([tokengateway README](https://github.com/eduardopessin/tokengateway)). Enforcement races are acknowledged rather than solved: ocp's quotas "are best-effort. Under concurrent bursts a key can exceed its cap by up to the server's max-concurrency (default 8), and cache hits are not counted toward quota" ([ocp lan-mode.md](https://github.com/dtzp555-max/ocp/blob/main/docs/lan-mode.md)); LiteLLM's reservation pattern is the only documented mitigation.

For the dashboard itself, the field is uniform. Local monitors and gateways alike show KPI tiles (cost, tokens, requests, users), time series of tokens and cost by day split by model and token type, cache-read versus cache-creation with a hit ratio, leaderboards, day-of-week by hour heatmaps, and for the active window a progress bar, burn rate in tokens per minute and projected exhaustion time ([ccusage README](https://github.com/ryoppippi/ccusage/blob/main/apps/ccusage/README.md); [Grafana 25255](https://grafana.com/grafana/dashboards/25255-claude-code-metrics-prometheus/); [claude-code-stats](https://github.com/AeternaLabsHQ/claude-code-stats)). The dominant lightweight stack is a single Python process (stdlib `http.server` or FastAPI) writing SQLite and serving a static Chart.js page; phuryn/claude-usage does this with zero dependencies ([phuryn/claude-usage](https://github.com/phuryn/claude-usage)). Nobody in this niche chose Streamlit, and Grafana appears only where OTLP metrics already exist; Claude Code emits `claude_code_token_usage_tokens_total` and `claude_code_cost_usage_USD_total` with `user_email` and `model` labels when telemetry is on, so a proxy that emits the same metric names could reuse the published Grafana dashboards unchanged. Cache hit ratio has no canonical definition in the sources (the usual form is `cache_read / (input + cache_creation + cache_read)`) and should be stated on the panel. The two ideas worth borrowing beyond the standard set are claude-code-stats' subscription ROI panel (API-equivalent value versus subscription fee) and an account-level "official utilization" gauge from the headers so the admin sees how close the shared account is to being throttled.

## Anthropic prohibits the core use case and has escalated enforcement all year

The policy risk is not a gray area for the specific pattern in the brief. The Consumer Terms (effective Oct 8, 2025), which govern Free, Pro and Max, state "You may not share your Account login information, Anthropic API key, or Account credentials with anyone else or make your Account available to anyone else" and prohibit access "through automated or non-human means" except via an API key ([Consumer Terms](https://www.anthropic.com/legal/consumer-terms)). The Claude Code legal page, whose "Authentication and credential use" section was added on Feb 19, 2026, says OAuth "is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications", that "Anthropic does not permit third-party developers ... to route requests through Free, Pro, or Max plan credentials on behalf of their users", that "developers may not collect, store, or intermediate Claude.ai credentials or session tokens", that "Advertised usage limits for Pro and Max plans assume ordinary, individual usage", and that Anthropic "may [enforce] without prior notice" ([Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)). The hosting section adds that "Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential", while explicitly permitting an organisation to provision its *own API key* to its own authorised users.

Enforcement has moved in steps. On Jan 9, 2026 server-side checks began rejecting subscription OAuth from OpenCode, Cline and others with "This credential is only authorized for use with Claude Code and cannot be used for other API requests", with Anthropic's Thariq Shihipar saying "we tightened our safeguards against spoofing the Claude Code harness" ([paddo.dev](https://paddo.dev/blog/anthropic-walled-garden-crackdown/)). Anthropic said it identified the traffic via "unusual traffic patterns" lacking normal telemetry ([The Register](https://www.theregister.com/2026/02/20/anthropic_clarifies_ban_third_party_claude_access/)). On Mar 19-20 a legal request led OpenCode (~127k stars) to remove its Anthropic OAuth plugin, reaching #1 on Hacker News with 470 points ([zbuild.io](https://www.zbuild.io/resources/news/opencode-blocked-anthropic-2026)). On Apr 4 Anthropic announced subscription limits would no longer cover "third-party harnesses including OpenClaw", with Boris Cherny explaining "subscriptions weren't built for the usage patterns of these third-party tools" ([TechCrunch](https://techcrunch.com/2026/04/04/anthropic-says-claude-code-subscribers-will-need-to-pay-extra-for-openclaw-support/)). On May 13 it reinstated programmatic use through a separate monthly "Agent SDK credit" pool reported at $20 (Pro), $100 (Max 5x) and $200 (Max 20x); this rests on a single VentureBeat article and the ocp and dario READMEs report that the change was then paused on its June 15 effective date ("For now, nothing has changed") ([VentureBeat](https://venturebeat.com/technology/anthropic-reinstates-openclaw-and-third-party-agent-usage-on-claude-subscriptions-with-a-catch); [ocp README](https://github.com/dtzp555-max/ocp)). The billing model for anything other than a human typing into the official CLI is therefore in flux, and a proxy's economics could change with a support-article edit.

The projects themselves draw the line in the same place. maxpool: "Never share accounts across people (that is the clear violation), and never add IP/residential proxies, fingerprint spoofing, or MITM. Those are the documented ban triggers"; and "**Multiplexing is a detectable pattern.** Many accounts fronted by one machine, with parallel sessions and fast token rotation, looks like the anomaly Anthropic's automated systems flag... People have lost accounts to pattern detection" ([maxpool README](https://github.com/2solarmax/maxpool)). ocp: "The defensible framing is **'one person, your own devices'** — sharing with friends or a team is not" ([ocp lan-mode.md](https://github.com/dtzp555-max/ocp/blob/main/docs/lan-mode.md)). claude-relay-service opens with a ToS-risk warning and disclaims responsibility for bans ([README](https://github.com/Wei-Shaw/claude-relay-service)). dario: "**I can't promise you won't be actioned, and I'd be skeptical of anyone who does.**" ([dario README](https://github.com/askalf/dario)). teamclaude's compliance essay argues own-accounts-plus-real-CLI-plus-human is consistent with the terms, yet ships the MITM mode and residential-egress option that maxpool calls ban triggers ([teamclaude docs/compliance.md](https://github.com/KarpelesLab/teamclaude/blob/main/docs/compliance.md)). claude-code-limiter, the project most directly built for the team-on-one-account case, has no disclaimer and an unanswered issue arguing it is "built entirely on top of the prohibited behavior" and that "Shared-account usage is fairly easy for Anthropic to detect (concurrent sessions, multiple machines/locations on one account)" ([issue #4](https://github.com/howincodes/claude-code-limiter/issues/4)). The detection signals named across sources are concurrent sessions from several machines or locations, missing Claude Code telemetry and headers, non-Claude-Code request shapes and IP multiplexing. Notably, a transparent proxy for genuine Claude Code clients *reduces* two of those signals (all traffic comes from one IP with the real CLI's request shape) while leaving the third (interleaved concurrent conversations that no single human could produce) fully visible. No primary source quantifies bans for shared-account proxies; the evidence is READMEs and press.

The sanctioned alternative for 2-3 people is Claude for Teams: Standard seats at $25/month ($20 annual) and Premium at $125/month ($100 annual), minimum two members, per-member 5-hour/weekly limits, and "Organization-level and individual spending caps" on usage credits billed at API rates once the seat allowance is exhausted ([Team plan](https://support.claude.com/en/articles/9266767-what-is-the-team-plan); [Manage usage credits](https://support.claude.com/en/articles/12005970-manage-usage-credits-for-team-and-seat-based-enterprise-plans)). Its analytics have a gap relevant to the brief: the spend CSV "only reflects spend that exceeds your seat allotment", and admins do not get each member's included-usage bars ([View usage analytics](https://support.claude.com/en/articles/12883420-view-usage-analytics-for-team-and-enterprise-plans)). The other sanctioned pattern is a Console API key behind an LLM gateway using `ANTHROPIC_AUTH_TOKEN` plus `ANTHROPIC_BASE_URL`, where per-user budgets and dashboards come from LiteLLM or Bifrost and Anthropic itself lists LiteLLM as a gateway enterprises use ([Manage costs](https://code.claude.com/docs/en/costs)). Everything in this report's technical sections applies unchanged to that legitimate configuration except the OAuth handling, which simply disappears.

### How the uncited ChatGPT summary holds up

The user-supplied ChatGPT design summary is uncited and must be treated as unverified, but most of its architectural advice agrees with the cited notes: transparent reverse proxy via `ANTHROPIC_BASE_URL` rather than CLI wrapping, hashed virtual keys, single-flight OAuth refresh, treating OAuth endpoints and headers as unstable, parsing SSE usage while forwarding, keeping account utilization separate from observed per-user tokens, labelling any per-user share of quota as an estimate, a FastAPI + SQLite + Chart.js dashboard, and a statusline script polling a gateway endpoint. Its "never conflate account quota, observed usage and local allocation" principle is exactly the conclusion the cited evidence forces. Three of its claims diverge. First, it calls **claude-code-limiter "the closest match for per-user quotas + admin dashboard"**; the cited notes show it is not a proxy at all, counts prompts rather than tokens, is in early beta with a broken Docker dashboard, and has been unmaintained since March 2026, whereas devasheeshG/claude-code-proxy and the Wei-Shaw gateways are the actual full matches, none of which the summary names. Second, it calls **OCP** the reference for "multi-user virtual keys and centralized credential handling"; ocp is a CLI subprocess wrapper that cannot serve Claude Code clients, its per-key quotas count requests only and are "best-effort" under concurrency, and its own docs say the per-key modes are "**not** a security isolation boundary". Third, its list of proposed limit types includes "optional allocation of shared quota between users" as if it were a known pattern; no surveyed project implements it, and the cited notes explain why the whole-percent, multi-bucket, cache-sensitive utilization signal makes it hard. The summary also omits the most consequential technical facts in the notes (the three kinds of 429, prompt-cache scoping to the account, the Node HTTP/2 stall, the usage endpoint's per-token throttling and schema drift) and understates the policy position, describing it as "Anthropic has restricted third-party OAuth use" rather than as an explicit prohibition on intermediating credentials and sharing accounts that has been enforced legally and technically throughout 2026. Its recommendation of TeamClaude and LiteLLM/Bifrost/Kong as pattern references is well supported by the notes.

## Conclusion

The research reframes the build question. Technically, a 2-3 user proxy with per-user token budgets and a Chart.js dashboard is a small project whose hard parts are already solved in readable open source: devasheeshG's SSE accumulator and quota normaliser, teamclaude's 429 taxonomy and cache-pinning rules, dario's wire-shape capture, and LiteLLM's budget-reservation and multi-window schema. The one feature nobody has built, share-of-account quota, is unbuilt for a reason: Anthropic exposes a whole-percent, per-bucket, cache-sensitive account gauge with no per-consumer breakdown, so the honest implementation is an admin-configured fraction applied to token-weighted attribution and displayed as an estimate, never as an Anthropic-reported fact.

The larger implication is that the *sharing* half of the brief, not the *metering* half, is the liability. Every line of metering, limiting and dashboard code transfers intact to the two configurations Anthropic explicitly permits, namely Team seats or a Console API key behind the same proxy with `ANTHROPIC_AUTH_TOKEN`, while only the OAuth-injection layer is the part that violates the Consumer Terms and the Claude Code legal page and that a February-2026-style server change could disable overnight. A design that keeps the credential backend pluggable, so the same per-user ledger and limits can front a subscription grant today and an API key or per-user logins (LiteLLM's pass-through mode) tomorrow, is the one that survives the policy volatility the sources document.
